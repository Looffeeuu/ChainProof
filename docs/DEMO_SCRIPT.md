# ChainProof 答辩演示脚本

## 第 1 节 · 环境准备

### 启动 Fabric 网络

```bash
cd chaincode
./network.sh up createChannel -c chainproof -ca
./network.sh deployCC -ccn chainproof -ccp ../chaincode/chainproof-contract -ccl javascript
```

### 启动后端

```bash
cd backend
npm install
npm run demo:reset    # 重置演示数据
npm start
```

### 启动前端

```bash
cd frontend
npm install
npm run dev
```

### 验证环境

- 前端：http://localhost:5173
- 后端：http://localhost:3000
- Fabric：Org1 + Org2 + Orderer 运行中

### 异常场景（备用）

- 上传文件后修改一个字节再上传 → FILE_HASH_MISMATCH
- 非成员尝试确认 → MEMBER_NOT_REVIEWER
- 已确认成员再次确认 → ALREADY_DECIDED

### 问题回答草稿

#### Q1: 为什么用 Fabric，不用以太坊等公链？

**团队、学院、评审机构之间是有准入的联盟关系。** Fabric 有成员身份和背书策略，没有 gas 费用，数据不对公网公开。

联盟链适合「已知参与方、需要权限控制」的场景，公链适合「匿名、开放」的场景。课程项目涉及学生成绩和作品，不适合公开链。

（PPT 第 1 页）

#### Q4: 管理员直接改 peer 上的状态数据库会怎样？

**只改到本地一个节点。** 默认背书策略需要多数组织共同背书，被改的节点读出的数据会和其他节点不一致；区块本身用哈希串联，历史交易改不了。

 Fabric 的信任模型是「多数组织共同背书」，不是「单个节点可信」。

（PPT 第 5 页）

#### Q7: 为什么统计不用浮点数？

**多个背书节点必须得到完全相同的读写集。** 浮点运算和本地化排序可能不一致，所以用整数加最大余数法，并按字节序排序。

联盟链合约的硬约束是「确定性」——所有节点执行相同交易必须得到相同结果。

（PPT 第 7 页）
